This section presents the~cost model and~the~two end-to-end scenarios
used to~validate IJM on~the~two-node cluster.  Scenario~1 exercises the
single-type profile sweep and~the~deadline-driven URGENT migration.
Scenario~2 adds a~second job type and~forces a~2-GPU placement to~meet a
tight deadline.  The~last subsection collects implementation notes
accumulated while bringing the~scenarios to~a~reproducible state.

\section{Objective and cost model}
\label{sec:e2e-objective}

The scheduler minimises
\[
\textsc{TotalCost} \;=\; \sum_{j} \texttt{GPUcost}(j)
  + \sum_{j} \texttt{TardWeight}(j) \cdot \max\bigl(0,\,\texttt{finish}(j)-\texttt{deadline}(j)\bigr),
\]
where \texttt{GPUcost} is~wall-clock $\times$~hourly rate
(Table~\ref{tab:e2e-rates}, left) and~\texttt{TardWeight} scales with
priority (right).  Slack deadlines favour the~cheapest bundle; deadline
pressure shifts urgent jobs onto the~fastest available.

\subsection{Proxy vs.\ true objective}

The cost above is~the~modelled objective.  The~C++ optimiser's
per-decision proxy
(\texttt{proxy\_function\_min}\,/\,\texttt{proxy\_function\_max} in
GPUspb) is~a~cheaper surrogate.

In the~minimisation form used by~\texttt{method=RG}, tardiness is
evaluated at~the~\emph{next-event horizon}
$\textsc{sim\_time}{=}\textsc{current\_time}{+}\textsc{first\_finish\_time}$
rather than at~each job's predicted completion.  A~placement on~slow
hardware therefore contributes zero in-proxy tardiness as~long as~the
deadline is~still in~the~future at~that horizon.

Combined with~the~$100{\times}$ multiplier the~proxy applies to~the
worst-case tardiness of~jobs left \emph{unscheduled} in~a~candidate
plan, this explains the~URGENT-on-\texttt{P600$\times$2} landing
observed in~our runs.  With~the~proxy reading zero tardiness for~every
URGENT placement, the~only term that distinguishes the~options is~the
worst-case tardiness of~jobs the~plan would have to~drop.  Any plan that
keeps every job scheduled wins over a~plan that does not.

The proxy never names ``preemption'': it~just penalises ``unscheduled
in~this plan''.  The~\texttt{proxy\_function\_max} variant
(\texttt{method=PR}) uses per-job \texttt{sch.get\_selectedTime()}
instead and~is~deadline-aware, but~it~is~not the~default.  We~keep
\texttt{method=RG} throughout to~mirror the~reference deployment.  The
behaviour is~present on~every actively-maintained upstream GPUspb branch
as~of~2026-01.

\subsection{Why URGENT lands on the slowest 2-GPU bundle}
\label{sec:e2e-s1-urgent-math}

A~naïve reading of~Table~\ref{tab:e2e-s1-urgent} suggests A40$\times$2
should win: it~is~the~only plan that meets URGENT's 10-minute deadline at
full job length.  The~captured run instead places URGENT on
\texttt{matemagician}~P600$\times$2 at~$t{=}8.0$\,min, migrates it~to
\texttt{polimi-gpu}~A40$\times$1 at~$t{=}11.0$ once JOB2 finishes,
and~finally upgrades it~to~A40$\times$2 at~$t{=}13.5$ when JOB1
finishes.  URGENT completes at~$t{=}27.5$\,min --- $10$\,min past
its deadline.  The~$+30$-minute patient deadlines are deliberately
loose (a preempted patient could re-run on~any bundle and~still
finish on~time), so the~``true'' cost of~preempting one is~near zero
--- yet the~proxy never proposes such a~plan.

Three proxy mechanics combine to~force this choice; we~unpack them
below.

\begin{enumerate}\itemsep0pt
\item \textbf{Horizon-myopic tardiness.}
\texttt{proxy\_function\_min} evaluates each job's tardiness at
$\textsc{sim\_time}{=}\textsc{current\_time}{+}\textsc{first\_finish\_time}$,
where \texttt{first\_finish\_time} is~the~soonest currently-scheduled
finish.  At~URGENT's arrival, the~A40 patients have $\sim$30~ep
remaining on~A40$\times$1 ($\approx 125$\,s); URGENT is~200\,ep ahead
on~any bundle, so it~cannot finish in~this horizon.  Its deadline
($+10$\,min$=600$\,s) is~still in~the~future at~\textsc{sim\_time}, so
\emph{every} URGENT placement gets in-proxy tardiness~$=0$.  Tardiness
drops out of~the~URGENT-on-X vs.~URGENT-on-Y comparison.

\item \textbf{Plans that drop a~runnable job pay the~$100{\times}$
\texttt{worstTardiCost} penalty.}
The proxy has no~explicit ``preempt'' term: for~every candidate schedule
it~loops over jobs and~charges \texttt{vmCost}~$+$~\texttt{tardiCost}
for~the~scheduled ones and
$100\cdot\max(\textsc{current\_time}{+}\textsc{maxExecTime}{-}\text{deadline},\,0)\cdot w_{\text{prio}}$
for~the~unscheduled ones (\texttt{sch.isEmpty()},
\texttt{scheduler.cpp}~L178--189).  Putting URGENT on~A40$\times$1
leaves one priority-4 patient unscheduled; A40$\times$2 leaves both.
Each evicted patient's \texttt{maxExecTime} is~its 75-epoch wall on~the
\emph{worst} eligible bundle (P600$\times$1, $\approx 3461$\,s), so even
though the~patient could re-run on~A40 and~meet its $+30$-minute
deadline in~practice, the~proxy charges
$100\cdot(7.5\,\text{min}+3461\,\text{s}-30\,\text{min})\cdot w_4
\approx \$83$ per~displaced patient.  A40$\times$2 doubles that.  In
practical terms, any plan that leaves a~runnable \texttt{cnn\_big}
patient unscheduled is~two orders of~magnitude more expensive than any
plan that keeps everyone scheduled --- even when, in~reality,
the~patient has enough slack to~be safely preempted and~re-run.

\item \textbf{P600$\times$2 vs.\ P600$\times$1: the~WorstTardy
tiebreaker.}
Both P600 plans keep every job scheduled (\texttt{matemagician} was
empty post-sweep), so neither pays the~$100{\times}$ unscheduled
penalty.  The~remaining differentiator is~the~in-schedule
\texttt{tardiCost} at~horizon~--- $0$ for~both at~$t{=}7.5$~--- plus
URGENT's own \texttt{maxExecTime}-tardy, which the~proxy uses when
ordering equal-tardiness plans.  URGENT's worst case on~P600$\times$1 is
153.8\,min (143.8\,min late); on~P600$\times$2 it~is~91.7\,min
(81.7\,min late).  P600$\times$2 has the~smaller absolute worst-case,
which is~enough to~break the~tie.
\end{enumerate}

Once URGENT is~actually running on~P600$\times$2 it~becomes part of
\texttt{currentSched}.  The~next opt round at~$t{\approx}11.0$ sees
JOB2 succeeded (its A40$\times$1 slot freed) and
\texttt{first\_finish\_time} now anchored on~JOB1.  Re-running the
same proxy with~URGENT already running on~P600$\times$2, migrating
it~to~the~now-free A40$\times$1 is~cheaper because URGENT's projected
completion collapses from~91.7\,min to~13.9\,min; in-proxy URGENT
tardiness drops accordingly and~the~GPU-rate increase is~two orders
of~magnitude smaller in~dollars.  Two rounds later, when JOB1 also
completes at~$t{\approx}13.5$, the~second A40 frees and~URGENT
upgrades to~A40$\times$2.

The literal answer to~``why does not a~very tardy job take the~fastest
bundle from the~start?'' is~the~following.  Under \texttt{method=RG} the
proxy sees only one event into the~future, so URGENT's intrinsic
deadline-loss is~invisible at~the~moment of~placement.  Meanwhile, any
plan that drops a~runnable patient~--- the~only way to~free an~A40
slot~--- pays the~$100{\times}$ \texttt{worstTardiCost} penalty.  The
optimiser's choice is~mechanically forced toward the~slowest bundle
that keeps everyone scheduled.  The~cluster converges to~A40$\times$2
through two or~three migrations rather than a~single decision.
\texttt{method=PR} would pick A40$\times$2 from the~first round, but
we~keep \texttt{method=RG} as~the~reference deployment.

\subsection{Settled steady state (before URGENT)}

PIN-A and~PIN-B (\texttt{cnn\_big}, prio~5, $+10$-min deadline) settle
on~\texttt{polimi-gpu}~A40$\times$1.  P600$\times$1 was rejected because
its 68-min wall would overrun the~10-minute deadline.  P-LSTM-1 and
P-LSTM-2 (\texttt{lstm-small}, prio~1, $+8$-h deadline) settle on
\texttt{matemagician}~P600$\times$1, the~cheapest bundle for~a~slack
\texttt{lstm-small}; the~A40 slots are closed by~the~priority-5 pins.

\subsection{Measured cascade}

URGENT is~placed on~\texttt{matemagician}~P600$\times$1 in~$\sim$10\,s
at~$t{\approx}7.5$\,min, preempting one lstm-small patient.  About
$1.5$\,min later, at~$t{\approx}9$\,min, the~optimiser upgrades URGENT
to~P600$\times$2 (the~second lstm-small is~displaced) --- the~proxy
re-evaluates with URGENT now in~\texttt{currentSched}, sees its
sluggish P600$\times$1 finish time, and~accepts the~co-location.  URGENT
runs on~P600$\times$2 from~$t{\approx}9$ to~$t{\approx}15$.  When PIN-B
finishes at~$t{\approx}10$ and~PIN-A at~$t{\approx}14$, the~A40 slots
free; the~optimiser migrates URGENT to~A40$\times$1 at~$t{\approx}15$
(only $\sim$2\,min of~work remains, so the~$\times$2 upgrade isn't
worth the~kill-drain cost).  URGENT completes at~$t{\approx}17.5$,
well inside its~$+22$-min deadline.  The~two lstm-small patients
resume on~the~freed P600 slots and~train through~$t{\approx}43$\,min;
one of~them (P-LSTM-2) also briefly held an~A40$\times$1 slot during
its~A40 profile sweep before migrating back to~P600.  PIN-A and~PIN-B
are untouched throughout: their priority-5 plus tight-deadline status
prices any A40-eviction cascade out of~reach.

\section{Implementation notes}
\label{sec:e2e-impl}

The captured scenarios are reproducible only because of~five fixes
discovered while bringing them up.  Each is~documented in~the~same
shape: symptom, root cause, fix, measured effect.

\subsection{Slot-tracker race on quick stop/run pairs}

\textbf{Symptom.}  Under \texttt{method=PR}, a~migration occasionally
produced a~\texttt{FAILED ec=1}.  \textbf{Root cause.}  A~\texttt{/stop}
and~a~\texttt{/run} issued to~one worker within milliseconds arrived
out~of~order, and~the~new container started before the~previous CUDA
context drained.  \textbf{Fix.}
\texttt{job\_dispatcher.\_await\_inflight\_stops\_on} makes every
\texttt{dispatch\_with\_slot} await any in-flight \texttt{/stop} on~the
same node (bounded 30\,s) before issuing \texttt{/run}.

\subsection{Worker progress-lag and stop-drain stalls}

\textbf{Symptom.}  On~\texttt{polimi-gpu}, the~stdout reader fell
progressively behind the~trainer; an~auto-preempt drain accumulated the
backlog and~overran the~60\,s drain-timeout safety net.  \textbf{Root
cause.}  The~reader (\texttt{worker/execution.py}) used to~open a~fresh
PostgreSQL connection over the~SSH-tunnelled link for~every per-epoch
\texttt{UPDATE jobs SET progress}; the~TCP$+$SSH$+$psycopg handshake
cost $\sim 5$\,s per~write, so lag grew by~$\sim 5$\,s per~epoch.
\textbf{Fix.}  The~reader now pushes only the~latest progress into a
shared slot; a~coalescing background writer flushes via~a~short-lived
connection at~most once per~second.  \textbf{Effect.}
Trainer-vs-worker timestamps match in~real time, and~the~drain after a
manual or~auto-preempt completes in~$\sim 5$\,s rather than colliding
with~the~60\,s ceiling.

\subsection{Profile-claim lifecycle thrash}

\textbf{Symptom.}  Instances occasionally fell into a
claim$\to$wipe$\to$claim loop that never converged.  \textbf{Root
cause.}  Profile cell claims (rows in~\texttt{profiling\_results} with
\texttt{duration\_seconds IS NULL}) were garbage-collected by~a~hot-path
sweep at~the~start of~every scheduling round.  A~transient
\texttt{is\_profiling\_run=FALSE} window during
\texttt{\_persist\_assignment} was enough for~the~sweep to~delete a
live claim.  \textbf{Fix.}  The~sweep is~replaced by~explicit cleanup
at~the~lifecycle events that own the~claim's fate: \texttt{DELETE
/jobs} (single and~bulk) drops the~instance's unmeasured claims inline,
and~the~worker drops them when a~profile or~standard run transitions to
\textsc{failed} (\texttt{worker/execution.py},
\texttt{worker/reconcile.py}).  A~single long-lease garbage collector
in~the~60-minute \texttt{\_queue\_watcher}
(\texttt{ProfilingScheduler.gc\_orphaned\_claims}) removes claims older
than 15~min whose owner is~no~longer in~\textsc{queued} or
\textsc{profiling} with \texttt{is\_profiling\_run=TRUE}.  The~hot path
is~now sweep-free.

A related fix changes the~profile-placement view of
\texttt{get\_node\_gpu\_usage} to~skip cross-instance in-flight claim
reservations (\texttt{include\_cross\_instance\_claims=False}).  The
standard-placement path still includes them; their original role of
protecting a~reserved cell from a~competing standard run remains
correct.  Counting them for~profile placement, however, mutually
blocked peers competing for~the~same physical cell, producing the~same
thrash from a~different angle.  The~node-slot semaphore is~the~real
arbiter at~dispatch time, so for~profile placement only
actually-running jobs are counted.

\subsection{Reaper-wake gap after migrate-preempts}

\textbf{Symptom.}  A~migrate plan that preempted URGENT via~the planned
channel occasionally left URGENT in~\textsc{queued} for~$\sim$23
minutes before the~60-minute watcher fired.  \textbf{Root cause.}
Splitting \texttt{ijm\_slot\_freed} into a~terminal channel (which
wakes the~optimiser) and~a~planned channel (semaphore-release only)
removed the~original RG-cascade idle gap, but~it~did not cover the~case
where \texttt{\_reset\_stuck\_queued\_assignments} cleared the
assignment and~cancelled the~dispatch task: no~wake source remained.
\textbf{Fix.}  The~reaper now sets \texttt{notify\_event} whenever it
actually reset at~least one row (\texttt{backend/src/app.py}), so the
next optimiser cycle re-places the~orphan immediately.

\subsection{Cross-version checkpoint compatibility}

The captured Scenario~1 run exercises checkpoint compatibility in~two
directions.  JOB1 saves on~\texttt{matemagician} (torch~1.5.1) and
reloads on~\texttt{polimi-gpu} (torch~2.6); the~URGENT cascade victim
JOB4 saves on~\texttt{polimi-gpu} and~reloads on~\texttt{matemagician}.
Both rely on~the~legacy pre-1.6 \texttt{torch.save} format and
\texttt{strict=False} load (\texttt{runtime/base.py}).
