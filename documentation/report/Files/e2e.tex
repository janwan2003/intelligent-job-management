This section presents the~cost model and~the~two end-to-end scenarios
used to~validate IJM on~the~two-node cluster.  Scenario~1 stresses the
single-type profile sweep and~the~deadline-driven URGENT migration;
Scenario~2 mixes types so the~A40 slots are~held by~tight-deadline
\texttt{cnn\_big} pins and~the~P600 slots by~slack~\texttt{lstm-small}
patients.  Both runs expose the~same horizon-myopia behaviour
in~upstream GPUspb.  Implementation notes accumulated while making
the~scenarios reproducible are collected in~\S\ref{sec:e2e-impl}.

\section{Objective and cost model}
\label{sec:e2e-objective}

The scheduler minimises
\[
\textsc{TotalCost} \;=\; \sum_{j} \texttt{GPUcost}(j)
  + \sum_{j} \texttt{TardWeight}(j) \cdot \max\bigl(0,\,\texttt{finish}(j)-\texttt{deadline}(j)\bigr),
\]
where \texttt{GPUcost} is~wall-clock $\times$~hourly rate
(Table~\ref{tab:e2e-rates}, left) and~\texttt{TardWeight} scales with
priority (right).  Slack deadlines favour the~cheapest bundle; deadline
pressure shifts urgent jobs onto the~fastest available.

\textbf{Cluster (idle) cost.}  Energy cost is~not the~only cost the
upstream optimiser models.  Its~\texttt{RG} proxy
(\texttt{proxy\_function\_min} in~\texttt{optimizer.cpp}) charges a
third, \emph{fixed} term~--- a~per-node \emph{idle cost}
$\sum_{n\ \mathrm{open}}\texttt{cost}_n\cdot\Delta t$ summed over~every
node hosting at~least one~job over~the~next-event horizon~$\Delta t$,
with~\texttt{cost}$_n$ sourced from~\texttt{nodes\_config.json}.  This
captures the~cluster's fixed cost~--- leasing, baseline power, cooling,
independent of~GPU draw~--- and~rewards consolidating jobs onto~fewer
open nodes, unlike the~per-GPU \emph{marginal} energy term above.  IJM
passes this per-node \texttt{cost} through to~the~optimiser, but~we~omit
it~from~\textsc{TotalCost} here: both nodes carry jobs throughout both
scenarios, so the~term is~a~constant offset that does~not change the
relative ranking of~the~plans we~compare.  We~therefore leave
\texttt{cost} at~small uniform placeholders and~do~not analyse it
further.

The cluster used throughout this section is~two profiling-capable
nodes, four slots total: \texttt{matemagician} with
2$\times$\texttt{QuadroP600} and~\texttt{polimi-gpu} with
2$\times$\texttt{A40}.  Hourly rates are as~in
Table~\ref{tab:e2e-rates}.  For each new job type the~profile sweep
exercises all four \texttt{(node, GPU-count)} cells
(\texttt{configs\_per\_job}{=}2, four instances).

\subsection{Proxy vs.\ true objective}

The cost above is~the~modelled objective.  The~C++ optimiser's
per-decision proxy
(\texttt{proxy\_function\_min}\,/\,\texttt{proxy\_function\_max} in
GPUspb) is~a~cheaper surrogate.

In the~minimisation form used by~\texttt{method=RG}, tardiness is
evaluated at~the~\emph{next-event horizon}
$\textsc{sim\_time}{=}\textsc{current\_time}{+}\textsc{first\_finish\_time}$
rather than at~each job's predicted completion.  A~placement on~slow
hardware therefore contributes zero in-proxy tardiness as~long as~the
deadline is~still in~the~future at~that horizon.

The proxy also applies a~$100{\times}$ multiplier to~the worst-case
tardiness of~jobs left \emph{unscheduled} in~a~candidate plan, but
that penalty only fires when a~candidate plan exists in~which a~job
ends up~\texttt{sch.isEmpty()} (i.e.\ has no~configuration left to
place it~on).  Combined with~Random Greedy's structure --- jobs are
placed in~priority order onto~\emph{currently-free} capacity only,
with no~speculative preemption of~incumbents --- three consequences
shape every URGENT placement we~observed.  First, when~every candidate
placement for~the arrival has its deadline still in~the~future at~the
horizon, the~proxy reads zero tardiness for~each of~them and~picks
the~one with~the~lowest \texttt{vmCost} regardless of~whether that
placement is~actually fast enough to~finish on~time.  Second, the
$100{\times}$ unscheduled penalty dominates any plan that leaves
a~prio-4-or-5 peer with no~configuration, so~when the~cluster is
oversubscribed at~arrival time the~optimiser will pick the~plan with
the~fewest unscheduled high-priority peers~--- typically by~routing
the~arrival to~the~slowest free bundle while keeping incumbents in
place.  Third, even when the~cluster has spare capacity, RG only ever
considers configurations whose slots are \emph{already free};
the~arrival cannot pre-empt an~incumbent peer to~take a~faster slot
because \texttt{Heuristic::assign} simply asks
\texttt{system.assign\_to\_node(...)} for~free capacity, gets~none,
and~falls through to~the~slower bundle.  Scenario~1
(\S\ref{sec:e2e-s1}) shows the~first and~third hitting together;
Scenario~2 (\S\ref{sec:e2e-s2}) shows the~second at~work.

The proxy never names ``preemption'': it~just penalises ``unscheduled
in~this plan''.  The~\texttt{proxy\_function\_max} variant
(\texttt{method=PR}) uses per-job \texttt{sch.get\_selectedTime()}
instead and~is~deadline-aware, but~it~is~not the~default.  We~keep
\texttt{method=RG} throughout to~mirror the~reference deployment.  The
behaviour described here is~the~one observed on~the~upstream GPUspb
checkout used for~this report.

\subsection{Why URGENT lands on the slowest 2-GPU bundle}
\label{sec:e2e-s1-urgent-math}

Table~\ref{tab:e2e-s1-urgent} ranks A40 plans first; the~run picks
P600$\times$2.  Three proxy mechanics combine to~force this choice.

\begin{enumerate}\itemsep0pt
\item \textbf{Horizon-myopic tardiness.}
\texttt{proxy\_function\_min} evaluates each job's tardiness at
$\textsc{sim\_time}{=}\textsc{current\_time}{+}\textsc{first\_finish\_time}$,
where \texttt{first\_finish\_time} is~the~soonest currently-scheduled
finish.  At~URGENT's arrival, the~A40 patients have $\sim$30~ep
remaining on~A40$\times$1 ($\approx 125$\,s); URGENT is~200\,ep ahead
on~any bundle, so it~cannot finish in~this horizon.  Its deadline
($+10$\,min$=600$\,s) is~still in~the~future at~\textsc{sim\_time}, so
\emph{every} URGENT placement gets in-proxy tardiness~$=0$.  Tardiness
drops out of~the~URGENT-on-X vs.~URGENT-on-Y comparison.

\item \textbf{Random Greedy never proposes a~plan that preempts an
incumbent.}
\texttt{Heuristic::assign} (the workhorse called by every greedy /
random-greedy iteration) calls
\texttt{system.assign\_to\_node(GPU\_type, n\_GPUs)} which only
returns a~node if a~currently-free slot exists; it~has no path that
displaces a~job already in~\texttt{currentScheduling}.  RG processes jobs in
priority order: URGENT first.  When URGENT asks for~A40, both A40
slots are already taken by~the~prio-4 patients in~currentSched, so
\texttt{assign\_to\_node} returns empty and~RG falls through to
\texttt{assign\_to\_suboptimal}, which iterates configurations in
cost-then-speed order using \emph{only} currently-free capacity.
The only configurations with free slots are P600$\times$1 and
P600$\times$2.  The~``preempt the~patient, place it~on~P600''
counter-plan that would let URGENT have A40 is~never even generated.

\item \textbf{P600$\times$2 vs.\ P600$\times$1: the~deadline-missing
fallback.}
Between the~two P600 configurations RG \emph{does} actually consider,
\texttt{Optimal\_configurations::get\_best\_setup} applies the~rule
``if a~configuration can meet the~deadline, pick the~cheapest;
otherwise, pick the~fastest''.
URGENT's 10-minute deadline cannot be met on either P600 bundle
(P600$\times$1$\,=\,$154.6\,min wall, P600$\times$2$\,=\,$92.3\,min),
so the~rule's fallback branch fires and~RG picks
\emph{fastest}~$=$~P600$\times$2.  P600$\times$1 would have been
cheaper per epoch, but~the~``cheapest'' branch only runs when the
deadline is~reachable; here it~is~not, so cost is~ignored.
\end{enumerate}

Once URGENT is~actually running on~P600$\times$2 it~becomes part of
\texttt{currentSched}.  The~next opt round at~$t{\approx}11.0$ sees
JOB2 succeeded (its A40$\times$1 slot freed) and
\texttt{first\_finish\_time} now anchored on~JOB1.  Re-running the
same proxy with~URGENT already running on~P600$\times$2, migrating
it~to~the~now-free A40$\times$1 is~cheaper because URGENT's projected
completion collapses from~92.3\,min to~10.4\,min; in-proxy URGENT
tardiness drops accordingly and~the~GPU-rate increase is~two orders
of~magnitude smaller in~dollars.  Two rounds later, when JOB1 also
completes at~$t{\approx}13.6$, the~second A40 frees and~URGENT
upgrades to~A40$\times$2.

\texttt{method=PR} (with \texttt{proxy\_function\_max}, deadline-aware
per~job) would pick A40$\times$2 from~the~first round, but~we~keep
\texttt{method=RG} as~the~reference deployment.

\section{Implementation notes}
\label{sec:e2e-impl}

Five issues surfaced while bringing the~scenarios to~reproducible
state; each is~summarised below and~detailed in~the~repo's
\texttt{CLAUDE.md} / commit messages.

\begin{itemize}\itemsep1pt
\item \textbf{Stop/run reorder race.}  A~migration's \texttt{/stop} and
\texttt{/run} could hit a~worker out~of~order under
\texttt{method=PR}, so the~new container started before the~previous
CUDA context drained; \texttt{dispatch\_with\_slot} now awaits any
in-flight \texttt{/stop} on~the~same node first.
\item \textbf{Per-epoch progress lag.}  Reader opened a~fresh
SSH-tunnelled PG connection per~epoch ($\sim$5\,s each) and~the
backlog could overrun the~60\,s drain timeout; reader now coalesces
into a~once-per-second background writer.
\item \textbf{Profile-claim thrash.}  A~hot-path sweep deleted live
claims during a~transient \texttt{is\_profiling\_run=FALSE} window;
replaced with lifecycle-event-driven cleanup plus a~15-min orphan GC
in~the~60-minute \texttt{\_queue\_watcher}.
\item \textbf{Self-inflicted optimiser wakes.}  Every slot-freed
\texttt{NOTIFY} woke the~optimiser, including notifies caused by~the
plan's own auto-preempts, so~RG re-ran on~partial state and~thrashed.
The~payload now carries a~reason; \texttt{auto\_preempt} is~swallowed
(the~plan's own dispatch picks~up~the~freed slot).  Migrate
plans are~staged in~\texttt{state.pending\_migrates} and~committed
by~the~slot listener once the~source \texttt{/stop} drains, so the
swallow doesn't strand them.
\item \textbf{Cross-version checkpoints.}  Pre-1.6
\texttt{torch.save}~$+$~\texttt{strict=False} load lets a~job migrate
between \texttt{matemagician} (torch~1.5.1) and~\texttt{polimi-gpu}
(torch~2.6) without losing progress; Scenario~1 exercises both
directions.
\end{itemize}
