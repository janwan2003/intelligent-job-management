This section presents the~cost model and~the~two end-to-end scenarios
used to~validate IJM on~the~two-node cluster.  Scenario~1 stresses the
single-type profile sweep and~the~deadline-driven URGENT migration on~an
\emph{under-subscribed} cluster; Scenario~2 mixes types and~fills every
slot, so the~A40 slots are~held by~tight-deadline \texttt{cnn\_big} pins
and~the~P600 slots by~slack~\texttt{lstm-small} patients.  Together they
expose how~upstream GPUspb's \texttt{method=RG} proxy behaves: Scenario~1
isolates its~\emph{horizon-myopia}~--- an~urgent job is~parked on~a~slow
but~free bundle because its deadline overrun is~invisible at~the
next-event horizon.  Scenario~2 fills the~cluster, so~the~same stateless
cost minimisation must drop the~cheapest slack work to~fit URGENT
(realised as~a~preemption); but~with~the~true per-epoch costs no
\emph{preemptible} bundle is~fast enough to~meet URGENT's deadline, so
the~myopia again parks it~on~the~cheapest slow bundle, and~the~deadline
is~met only once a~pin finishes and~URGENT migrates onto~fast~A40.
As~\S\ref{sec:e2e-objective} explains, the~optimiser never reasons about
preemption or~migration itself: it~just minimises a~stateless plan cost,
and~the~priority-aware \emph{outcome} in~Scenario~2 is~emergent.

\section{Objective and cost model}
\label{sec:e2e-objective}

IJM delegates standard-run placement to~GPUspb run with
\texttt{method=RG}.  We~report what that~optimiser \emph{actually}
minimises, since it~is~the~ground truth for~every placement we~observe:
per~scheduling decision, Random Greedy scores a~candidate plan with the
proxy \texttt{proxy\_function\_min} (\texttt{optimizer.cpp}):
\[
\begin{aligned}
\textsc{Cost}_\textsc{RG}={}&
  \sum_{\text{sched }j}\!\Big(r(b_j)\,\Delta t + w(p_j)\,[\,t_0{+}\Delta t-d_j\,]^{+}\Big)
  + \sum_{n}\texttt{cost}_n\,\Delta t \\
  &{}+ \lambda\!\!\sum_{\text{unsched }j}\!\! w(p_j)\,[\,t_0{+}T^{\mathrm{full}}_j-d_j\,]^{+},
\end{aligned}
\]
with indices $j$ (over~the~plan's scheduled/unscheduled jobs) and~$n$
(over~the~cluster's nodes), and~parameters ($[x]^{+}\equiv\max(0,x)$):
\begin{itemize}[leftmargin=*,itemsep=1pt,topsep=2pt]
  \item $\Delta t$~--- next-event horizon: the~soonest finish among the~plan's scheduled jobs;
  \item $t_0$~--- the~current time;
  \item $b_j,\,p_j,\,d_j$~--- job~$j$'s assigned GPU bundle, priority, and~deadline;
  \item $r(b)$~--- hourly rate of~GPU bundle~$b$ (Table~\ref{tab:e2e-rates}, left);
  \item $w(p)$~--- per-priority tardiness weight (Table~\ref{tab:e2e-rates}, centre);
  \item $\texttt{cost}_n$~--- per-node operating cost from \texttt{nodes\_config.json} (Table~\ref{tab:e2e-rates}, right), passed through in~the~optimiser request.  Note the~sum is~over~\emph{every} configured node: \texttt{compute\_nodeCost} charges $\texttt{cost}_n\Delta t$ whether or~not the~node hosts a~job (no~occupancy filter), so~this term gives no~consolidation incentive;
  \item $T^{\mathrm{full}}_j$~--- job~$j$'s full remaining run time on~its~\emph{slowest profiled bundle} (the~$\max$ over~the~job's measured configs, \texttt{get\_maxExecTime}), charged in~full and~\emph{not} clipped to~$\Delta t$;
  \item $\lambda$~--- unscheduled-job penalty multiplier, hard-coded to~$\lambda{=}100$ in~\texttt{proxy\_function\_min}.
\end{itemize}
Three features of~this objective drive everything the~scenarios show: the
GPU, tardiness, and~node terms of~\emph{scheduled} jobs are all charged
only up~to~the~horizon $\Delta t$, not~to~real completion (so~a~placement
that~will overrun a~far-off deadline still reads zero tardiness now);
an~\emph{unscheduled} job pays $\lambda{=}100$ times its~\emph{full}
worst-case tardiness (so~omitting a~high-priority, tight-deadline job is
ruinous and~omitting a~low-priority, slack one is~nearly free); and~there
is~no~migration or~preemption term~--- the~objective scores the~candidate
plan alone, ignoring what is~running (\S\ref{sec:e2e-proxy}).

$T^{\mathrm{full}}_j$ is~not~a~constant.  A~job's configs are~exactly the
bundles already profiled for~its~type, so as~the~profile sweep progresses
and~measures slower bundles, $T^{\mathrm{full}}_j$~--- the~slowest of
them~--- only grows.  While just~a~fast bundle is~known, even~an
unscheduled long job clears its~deadline at~$T^{\mathrm{full}}_j$, its
$\lambda$-penalty is~zero, and~it~is~free to~omit; the~instant a~much
slower bundle is~profiled (\texttt{QuadroP600} is~$\sim$15$\times$ slower
than~\texttt{A40} for~\texttt{cnn\_big}, Table~\ref{tab:e2e-bundle-costs}),
$T^{\mathrm{full}}_j$ jumps, and~a~long, tight-deadline job that~would now
miss on~that bundle flips from~free-to-omit to~\emph{must-schedule}~---
with~no~change in~free capacity.  Scenario~1's profile sweep
(\S\ref{sec:e2e-s1}) does exactly this: a~patient is~left unscheduled
while only~\texttt{A40} is~measured, then~forced onto a~slot the~moment
the~\texttt{QuadroP600} profile lands.

\subsection{Judging the~proxy: an~idealised yardstick}
\label{sec:e2e-proxy}

\textsc{Cost}$_\textsc{RG}$ is~what the~optimiser minimises, but~it~is
a~\emph{per-decision} surrogate.  To~judge its~choices we~compare against
an~\emph{idealised} full-run cost~--- the~same terms, but~with tardiness
(and~GPU/node cost) measured at~each job's \emph{real} completion instead
of~at~$\Delta t$.  The~gap between the~two is~what the~scenarios expose:

\begin{itemize}[leftmargin=*,itemsep=3pt,topsep=2pt]
  \item \textbf{Horizon-myopia (free slot $\Rightarrow$ Scenario~1).}  Charged only to~$\Delta t$, tardiness reads zero while a~deadline is~still in~the~future at~the~horizon~--- so~the~proxy parks an~urgent job on~a~cheap, free, far-too-slow bundle rather than~faster hardware it~would have to~clear first.
  \item \textbf{Drop-the-cheapest (full cluster $\Rightarrow$ Scenario~2).}  When jobs exceed capacity, every plan leaves someone unscheduled, and~the~$\lambda{=}100$ penalty drops whoever is~cheapest to~omit~--- smallest $w(p)\,[\text{lateness}]^{+}$.  On~the~true per-epoch costs the~same myopia also governs \emph{which} preemptible bundle then absorbs the~urgent job (the~cheapest, not~the~least-tardy), so~Scenario~2 exhibits both effects.
  \item \textbf{Preemption is~a~side effect.}  The~objective is~stateless (\S\ref{sec:e2e-objective}): the~optimiser picks a~target plan, and~IJM realises it~by~stopping whatever the~plan dropped~--- the~optimiser never reasons about preemption.
  \item \textbf{\texttt{method=PR} would~differ.}  The~deadline-aware variant scores per-job \emph{real} finish times and~would dodge the~horizon-myopia.
\end{itemize}

\subsection{Why URGENT lands on the slow free bundle}
\label{sec:e2e-s1-urgent-math}

The optimiser's own cost-minimal plan (Table~\ref{tab:e2e-s1-proxy})
parks URGENT on~the~slow free P600$\times$2.  Two features of~the~proxy
it~minimises combine to~produce this.

\begin{enumerate}\itemsep0pt
\item \textbf{Horizon-myopic tardiness.}
\texttt{proxy\_function\_min} evaluates every job's tardiness at
$\textsc{sim\_time}{=}\textsc{current\_time}{+}\textsc{first\_finish\_time}$,
where \texttt{first\_finish\_time} is~the~soonest finish in~the~plan.
URGENT is~200\,ep ahead on~any bundle, so~in~every plan that~keeps a~quick
prio-4 patient running it~is~a~patient that~finishes first (a~few minutes
out), \textsc{sim\_time} lands before URGENT's $+10$-min deadline, and~URGENT's
tardiness reads exactly~zero.  Tardiness thus drops out of~the~comparison
for~all the~cheap plans, even though in~truth the~P600$\times$2 placement
overruns by~$\sim$2.4\,h while A40$\times$2 would overrun by~only~$\sim$5\,min.
(The~one exception is~the~A40$\times$2 plan itself, where URGENT becomes
the~earliest finish and~the~horizon stretches far~enough to~register its
$\sim$310\,s of~tardiness --- which only makes that~plan look~\emph{worse}.)

\item \textbf{The~proxy bills over~that~same short horizon, and~re-plans
from~scratch.}
Each construction calls \texttt{close\_nodes()} first, wiping all
occupancy, so~the~score never contains an~``eviction cost'': it~rates
a~full plan in~isolation, with~no~notion of~which job was~already running
(\S\ref{sec:e2e-objective}).  With~URGENT's tardiness masked, the~cheapest
plan is~simply the~one with~the~smallest $\Delta t$ and~the~cheapest rates:
keep the~quick patients on~fast A40 (so~a~patient sets~$\Delta t\approx3$\,min)
and~drop the~200-epoch URGENT onto~the~free, cheapest-per-hour P600, where
its~GPU is~billed for~only those~$\sim$3\,minutes.  Every faster placement
scores worse: A40$\times$2 makes URGENT itself the~earliest finish,
stretching~$\Delta t$ to~$\sim$15\,min --- which inflates \emph{every} job's
GPU and~node charge and~exposes URGENT's own tardiness --- while putting
URGENT on~an~A40$\times$1 slot would charge the~$10\times$-dearer A40 rate
over the~horizon for~no~proxy gain (URGENT's~speed is~invisible).  With~the
whole P600 node idle, its~two free bundles tie at~the~bottom (cheapest
hourly rate, tardiness masked) and~RG takes the~2-GPU one.  No preemption
is~involved at~all here --- the~idle node absorbs URGENT without displacing
anyone.
\end{enumerate}

As~the~patients finish on~their own (JOB2 at~$t{\approx}10.9$, JOB1
at~$t{\approx}13.5$), the~optimiser migrates URGENT onto~A40~--- first
A40$\times$1, then~A40$\times$2~--- without displacing anyone; but~the
slow-P600 start and~staged migration leave it~$\sim$11\,min late.  (URGENT
cannot meet its~$+10$-min deadline on~\emph{any} bundle: even A40$\times$2
needs $\sim$15\,min for~200 epochs.)

\texttt{method=PR} (with~\texttt{proxy\_function\_max}, deadline-aware
per~job) would have~seen URGENT's true finish time from~the~first round
and~rushed it~onto A40$\times$2 immediately --- preempting both patients
up~front and~finishing $\sim$5\,min late instead of~$\sim$11 --- but~we
keep \texttt{method=RG} as~the~reference deployment.

\section{Scenario 2 --- two types, forced 2-GPU placement}
\label{sec:e2e-s2}

Scenario~2 introduces a~second job type and~\emph{fills} the~cluster.
Two priority-5 \texttt{cnn\_big} pins occupy the~A40 slots; two
priority-1 \texttt{lstm-small} patients occupy the~P600 slots.  An~urgent
\texttt{cnn\_big} (prio~5) then arrives with~a~$+22$-min deadline that, on
the~true per-epoch costs, \emph{no~preemptible} bundle can~meet: only A40
reaches it (3--4\,min for~40 epochs), but~the~A40 slots are~held by
equal-priority pins URGENT cannot evict, and~both P600 bundles overrun
(P600$\times$2 $\sim$31\,min, P600$\times$1 $\sim$52\,min).  With~no~free
slot anywhere, every plan leaves some job unscheduled, and~--- exactly
as~in~Scenario~1 --- the~horizon-myopic proxy reads URGENT's tardiness
as~zero, so~the~cheapest plan simply takes the~cheapest \emph{preemptible}
bundle, \emph{not} the~one that~minimises the~overrun: it~picks
P600$\times$1 and~drops the~single slack prio-1 \texttt{lstm-small} it~must
evict to~free that~slot (the~$+8$-h deadlines make the~patients almost
free to~omit).  URGENT therefore lands on~hardware that~misses its
deadline outright, and~only \emph{meets} it because, once a~pin finishes,
the~optimiser migrates it~onto the~freed A40, where it~completes with~time
to~spare.  The~contrast with~Scenario~1 is~thus narrower than it~first
appears: both scenarios show the~same myopia; here the~full cluster's
churn~--- preempting slack, then~migrating onto~freed fast hardware~---
happens to~recover the~deadline.

\section{Reproducibility}

All figures and~tables in~this chapter are derived from the~2026-06-25
run snapshots committed under
\texttt{documentation/report/e2e\_runs/2026-06-25/\{s1,s2\}/}
(\texttt{api.log}, \texttt{jobs.json}, \texttt{profiles\_*.json},
\texttt{chart\_s\{1,2\}\{,\_predicted\}.tex}).  These runs use~the
corrected per-epoch profiler --- the~worker records the~runtime's own
per-epoch compute time (warmup excluded), not~the~arrival interval of~its
log lines (\texttt{worker/profiling.py}, \texttt{execution.py}) --- so~the
per-bundle costs reflect true GPU throughput.  Per-bundle costs are taken
from \texttt{profiling\_results.duration\_seconds} and~the~hourly rates in
Table~\ref{tab:e2e-rates}; the~timeline charts are auto-generated from
the~run's API log by~\texttt{infra/generate\_chart\_tex.py} (and~the
predicted-finish overlay by~\texttt{generate\_chart\_tex\_predicted.py}),
so~every bar position comes from a~real log event.  Scenarios are driven by
\texttt{infra/e2e\_scenario.sh} and
\texttt{infra/e2e\_scenario\_2types.sh}; slot metrics are exposed at
\texttt{GET /admin/slots}, and~API logs land in~the~\texttt{ijm-api}
container (\texttt{docker logs ijm-api}) brought up~by
\texttt{infra/ijm up}.
