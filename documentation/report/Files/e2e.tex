These two end-to-end scenarios validate that IJM executes the~optimiser's
plan correctly across the~full job lifecycle: it~profiles each new job type,
places jobs on~single- or~dual-GPU bundles, preempts the~cheapest work
to~admit an~urgent job, and~migrates a~preempted job across nodes~---
resuming its checkpoint across torch versions~--- all while keeping its slot
accounting coherent.  Both runs are driven only by~\texttt{POST /jobs} on~the
two-node cluster (\texttt{matemagician}: 2$\times$QuadroP600;
\texttt{polimi-gpu}: 2$\times$A40).  Placement decisions come from~the~external
GPUspb optimiser (\texttt{method=RG}), which IJM consumes but~does not
implement; Appendix~\ref{app:proxy} documents that proxy's cost model and~a
\emph{horizon-myopia} it~exhibits~--- which explains why an~urgent job is
sometimes parked on~slow-but-free hardware~--- but~that is~a~property of~the
upstream optimiser, orthogonal to~IJM's own correctness.

them without dropping a~slot or~losing progress.
